Introduction
This report has been produced as part of Activity 1 for Unit 25: Full Stack Development. The purpose of this activity is to research and compare two existing healthcare or clinic management systems in order to inform the design and development of the Medical Record Management System (MRMS) for CareTrack Clinic. The research will consider system design, key features, full stack development principles, and how effectively each system serves the needs of its intended users.
CareTrack Clinic is a mid-sized private medical centre that currently operates using paper-based records and disconnected spreadsheets. The clinic requires a modern web-based system to manage doctor profiles, patient records, and disease/diagnosis histories. Researching existing systems allows us to identify industry best practices, understand the expectations of clinical users, and ensure that our own solution is appropriate and competitive.
The two systems selected for comparison are:
OpenMRS – a widely used commercial healthcare management platform.
OpenEMR – a leading open-source electronic medical records (EMR) system.
These systems were selected because they both operate in a similar domain to the MRMS, supporting patient record management, doctor profiles, appointment scheduling, and access control — features that closely align with CareTrack Clinic's requirements.

A.M1 - Analyse full stack development tools and technologies
To build an efficient, secure, and high-performance Medical Record Management System (MRMS), developers must strategically select and configure the entire full-stack ecosystem. Healthcare environments present a unique challenge: they require instant data retrieval across complex, interconnected datasets (such as linking doctors, patients, and continuous clinical histories) while maintaining strict security boundaries and high application uptime. 
An analysis of the full-stack architectural choices in OpenMRS and OpenEMR demonstrates how backend, frontend, and database layers harmonize to meet these rigorous demands.
Database
OpenMRS (Java / MySQL or PostgreSQL): OpenMRS utilizes a highly normalized, concept-driven relational model. To optimize performance and abstract complex SQL queries, it implements Hibernate as its Object-Relational Mapping (ORM) framework. Hibernate acts as the bridge between the Java backend and the relational database. It ensures strict data integrity—preventing orphaned records if a diagnosis is modified or a patient is reassigned. To maintain high performance during heavy concurrent usage, OpenMRS leverages Hibernate’s second-level caching. This minimizes direct database hits for frequently accessed data (such as standard ICD-10 code lists or doctor specialty configurations), drastically reducing server latency. 
OpenEMR (PHP / MySQL or MariaDB): OpenEMR communicates directly with MySQL or MariaDB databases using abstract data layers (like ADOdb or PDO). Unlike OpenMRS's abstract concept design, OpenEMR uses a more direct, structured relational schema where tables explicitly mirror real-world entities (e.g., patient_data, users, lists for diagnoses). To handle the high-throughput demands of a busy clinic, OpenEMR relies heavily on database indexing on primary and foreign keys (such as linking a provider's ID to patient charts). This ensures that when a clinician loads a comprehensive patient profile, the database executes rapid pointer lookups rather than performing exhaustive, resource-heavy full-table scans.
Backend
OpenMRS (Java Spring Framework): OpenMRS relies on a enterprise-grade Java Spring backend architecture. This multi-layered structure separates the controller, service, and data access layers. High performance is maintained through Spring's robust multithreading capabilities, allowing the server to handle asynchronous requests simultaneously (e.g., a receptionist registering a new patient while a clinician updates a disease record) without bottlenecking the processor. Furthermore, its backend enforces security via Aspect-Oriented Programming (AOP), injecting interceptors that evaluate a user's session role (Administrator vs. Clinician) at the service level before any data is processed or transmitted.
OpenEMR (PHP Engine): OpenEMR utilizes a server-side PHP architecture. Modern iterations of OpenEMR have optimized performance by migrating to PHP 8.x, which includes OPcache (Optimizer Plus). OPcache improves performance by storing precompiled script bytecode in the server’s shared memory, eliminating the need for PHP to load and parse scripts on every single page request. This makes page rendering and API execution significantly faster. For role-based security, OpenEMR processes an internal Access Control List (ACL) engine during the server-side compilation phase, selectively executing and injecting modules based on whether the verified user session matches administrative or clinical permissions.
Frontend
OpenMRS (Modern Frontend 3.0 - React / Microfrontends): In its modern architecture, OpenMRS has decoupled its frontend from the Java backend entirely, utilizing a React-based microfrontend architecture communicating via a headless RESTful API. This full-stack decoupling dramatically optimizes client-side performance. React's Virtual DOM updates only the modified elements of a webpage (such as appending a single new diagnosis entry) without forcing a full browser refresh. Data fetching is optimized through state-management libraries and hooks that cache API responses client-side, meaning a clinician can switch between a patient's diagnosis history and a doctor's schedule instantly without sending repetitive, redundant fetch requests back to the server.
OpenEMR (Hybrid Twig, JavaScript, and Bootstrap): OpenEMR operates on a more traditional server-side rendering (SSR) model, dynamically assembling HTML templates on the server before sending them to the browser, styled with Bootstrap. While SSR can occasionally result in full-page reloads when navigating across completely different modules, OpenEMR mitigates performance lags by integrating AJAX (Asynchronous JavaScript and XML) for intensive interactive components, such as its calendar scheduling and live search/filter fields. By utilizing asynchronous background requests, the client browser can query the PHP backend for updated doctor schedules or filtered patient lists dynamically, updating the active view seamlessly without disrupting the user's workflow. 
A.D1 - Evaluate how full stack development tools and technologies are applied
Evaluating the application of full-stack development tools in healthcare IT requires looking beyond mere technical capability; it demands an assessment of how effectively these technologies serve their non-technical endpoints: clinical safety, administrative throughput, data compliance, and organizational scalability.
By critically evaluating the real-world deployment models of OpenMRS and OpenEMR, we can determine the institutional trade-offs inherent to different full-stack methodologies and evaluate their suitability for a mid-sized facility like CareTrack Clinic.
1. Evaluation of OpenMRS
The core strength of OpenMRS lies in its highly normalized, "concept-driven" data layer managed via Hibernate.
The Positives: From an organizational and clinical perspective, this full-stack choice is highly effective. Because medical data is abstractly mapped, the system can adapt to any medical specialty (from general practice to cardiology or neurology) without requiring structural database migrations. New diagnosis criteria, custom symptoms, or regional ICD codes can be dynamically injected into the database layer via the user interface. Furthermore, its modern decoupled React frontend provides a responsive, desktop-like user experience that minimizes cognitive fatigue for clinicians documenting active patient encounters. 
The Negatives: This level of abstraction introduces significant architectural complexity. Because database records are highly split across "concepts" rather than structured in simple flat tables, executing a comprehensive patient profile query requires complex SQL JOIN operations across dozens of backend relational tables. If the system is not heavily optimized with advanced Hibernate caching, this can bottleneck server CPU performance during peak clinic hours, leading to sluggish page reloads. Organizationally, this means OpenMRS requires dedicated, specialized database administrators to maintain—a massive financial overhead for a mid-sized private medical centre. 
2. Evaluation of OpenEMR:
OpenEMR represents a traditional, tightly integrated server-side rendered (SSR) full-stack environment built on PHP and MySQL.
The Positives: OpenEMR excels in immediate operational accessibility and deployability. Because PHP compiles entirely server-side and outputs standard Bootstrap-styled HTML to the browser, the client-side system footprint is exceptionally lightweight. It runs seamlessly on legacy hardware or low-spec clinic computers, minimizing the need for expensive hardware upgrades. Its direct database schema (where a table explicitly represents patient_data) makes basic data filtering, data seeding, and custom reporting incredibly straightforward for local IT staff. This direct architecture easily satisfies basic clinical requirements like registering new patients and tracking histories without lag. 
The Negatives: The monolithic nature of a traditional PHP/Bootstrap stack introduces severe usability limits in high-tempo medical environments. Because the architecture relies heavily on server-side rendering, navigating between distinct system modules (e.g., jumping from a doctor's schedule to an extensive disease log) can trigger full browser refreshes. This disrupts clinical workflows compared to the instantaneous transitions of single-page applications (SPAs). Furthermore, scaling and maintaining a legacy monolithic codebase introduces significant technical debt; changes made to a UI template run the risk of inadvertently breaking tightly coupled backend database operations if strict testing boundaries are not continuously enforced.
Conclusion
This evaluation demonstrates that an optimal full-stack solution for a mid-sized practice must synthesize the core strengths of both systems while actively eliminating their engineering drawbacks.
Why Next.js Explains the Paradigm Shift: My choice to utilize Next.js for the CareTrack Clinic MRMS directly resolves the tensions uncovered in this evaluation. Next.js bridges the gap between OpenMRS’s frontend fluidity and OpenEMR’s lightweight server-side efficiency.
By leveraging React Server Components (RSC) alongside built-in API routes, the system achieves rapid initialization by handling heavy relational lookups (Doctors to Patients to Diagnoses) directly on the server. It then pipes data to the client as a high-performance single-page application. 
This full-stack synergy eliminates the full-page reloads found in OpenEMR, provides the client-side speed of OpenMRS, and avoids the severe server-side infrastructure overhead of a Java Spring Enterprise system. This delivers a robust, secure, and responsive system tailored perfectly to the operational constraints of CareTrack Clinic.

Technical Database Documentation
The relational database schema for the CareTrack Clinic Medical Record Management System (MRMS) has been designed using an entity-relationship framework to enforce strict data integrity, optimal relational indexing, and role-based access boundaries. 
The diagram below maps out the four primary data collections/tables: User (for system authorization), Doctor, Patient, and Disease.
1. Architectural Notation &amp; Key Constraints
The ERD utilizes Crow’s Foot notation to illustrate relational configurations and cardinalities:
PK (Primary Key): Unique identifiers assigned to enforce entity integrity.
FK (Foreign Key): Fields used to map relationships between separate data tables, enforcing referential integrity.
UK (Unique Key): Enforces fields that cannot contain duplicate records across different rows (e.g., system user email addresses).
2. Breakdown of System Relationships
The database schema strictly implements the structural business rules outlined by the CareTrack Clinic assignment parameters: 
Doctor to Patient (One-to-Many): A Doctor record can be linked to multiple Patient charts over time ("has many"). Conversely, each specific Patient profile is explicitly assigned to exactly one primary care Doctor via the doctorId foreign key constraint ("belongs to"). 
Patient to Disease/Diagnosis (One-to-Many): A Patient can compile multiple diagnostic events throughout their clinical timeline ("has many"). Each specific Disease record represents an isolated clinical entry that maps exclusively to a single Patient via the patientId foreign key constraint. 
User (Isolated Session Table): The User table handles localized system credentials and authentication properties. It operates independently from direct medical charting links to maintain an abstracted layer for role-based permissions (role: Administrator, Clinician, Receptionist).

Security &amp; Authentication
Bcrypt-Hashed Passwords: During registration (/sign-up), credentials are computationally hashed using bcryptjs before insertion into the MongoDB database, securing user passwords against database leaks.
JWT Session Persistence: Powered by NextAuth.js (Auth.js v5), utilizing JSON Web Tokens (JWT) for secure, stateless user sessions that persist across routes without overloading the database.
Role Ingestion: Users are dynamically assigned clinical roles (defaulting to Receptionist) that are embedded directly in the JWT payload for client and server-side authorization.
Role-Based Access Control System
The application enforces strict security bounds across its three user roles: Administrator, Clinician, and Receptionist. This prevents unauthorized personnel from accessing sensitive medical files or modifying system profiles.
Administrator:
Full CRUD (Create, Read, Update, Delete) permissions on Doctors, Patients, and Disease records.
Clinician:
Full view access to doctors and patients.
Permission to Create &amp; Edit Patient Diagnoses (Diseases).
Permission to Update Patient demographics, but cannot register new patients or manage doctor rosters.
Receptionist:
Permission to Register new patients and view active doctors/patients.
Strictly Blocked from viewing, adding, or modifying clinical disease diagnosis records (respecting patient confidentiality).

ACTIVITY 5  learning aim B and C. C.P6, BC.D2, BC.D3
C.P6 – Review the extent to which the MRMS meets CareTrack Clinic’s client requirements
CareTrack Clinic commissioned MediCore Solutions to replace paper records and disconnected spreadsheets with a web-based Medical Record Management System (MRMS). After completing design, development, testing and optimisation, I reviewed the final system against the original brief to judge how far it meets those needs.
The core functional requirements are largely met. The system supports full CRUD for doctors (name, specialty, department, contact details), patients (personal details and assigned doctor), and diseases/diagnoses (ICD code, description, severity and linked patient). The data model follows the required relationships: one doctor can have many patients, each patient belongs to one doctor, and each patient can have many diagnosis records. The patient profile page shows the assigned doctor and all linked diagnoses together, which was a key client requirement and removes the need to check multiple files or sheets.
Search and filter across doctors, patients and diseases are implemented, so staff can locate records quickly during busy clinic hours. Role-based access matches the scenario: administrators have full access including doctor management and settings; clinicians can view and update patient and disease records; receptionists can register new patients and view doctor information without access to change clinical diagnosis data they are not responsible for. Testing in Activity 4 confirmed that restricted roles cannot perform actions outside their permissions.
Some requirements from the wider scenario are only partly addressed. The brief also refers to referral management, after-hours emergency contact, appointment scheduling and fuller diagnosis reporting. The MRMS focuses on secure record management, registration and clinical data linking rather than every optional service CareTrack listed. For a first release this is acceptable, but the clinic would need further development if they expect the system to cover referrals and advanced reporting from day one.
Evidence from earlier activities supports this review. Activity 1 research showed what larger clinic systems offer; Activities 2 and 3 designs mapped screens and the ERD to client needs; Activity 4 testing and feedback documented fixes and improvements. Screenshots of CRUD operations, role tests and before/after changes show that requirements were tested, not only assumed. Overall, the MRMS meets the main client requirements for digital record management and role-based staff access, with clear scope for future features where the brief goes beyond the current build.
BC.D2 – Evaluate design decisions and the optimised MRMS against client requirements (user needs and fitness for purpose)
Design decisions were made to keep the system understandable for clinical staff, administrators and receptionists rather than optimised only for developers. Wireframes from Activity 2 covered the doctor list, patient profile, disease management and dashboard so each role had a clear entry point. The ERD and data dictionary defined doctor, patient and disease entities with the correct one-to-many links, which guided the database structure in development and reduced the risk of orphaned or inconsistent records.
Visual design used a simple layout with consistent navigation, clear headings and forms labelled in everyday language (e.g. specialty, severity, assigned doctor). Feedback in Activity 3 highlighted areas such as making actions more obvious and improving readability on smaller screens; those points were addressed in the final build through layout adjustments and clearer feedback messages after save or error actions. Not every suggestion was applied—some ideas would have added complexity without clear benefit for CareTrack’s daily workflow—but changes that improved usability for non-technical users were prioritised.
Technical choices were evaluated against fitness for purpose. A full stack approach with Next.js, API routes, Prisma and MongoDB allowed secure server-side handling of data and permissions. Compared with a spreadsheet or a generic booking app, this stack enforces relationships in the database and controls access through login roles, which better suits a clinic handling sensitive patient data. Compared with enterprise systems such as Epic or Cerner, the custom MRMS is smaller and easier to adapt when CareTrack requests changes, though it lacks deep hospital-wide features those products provide.
Optimisation after testing strengthened fitness for purpose. Compatibility checks on different browsers and devices showed the interface remained usable on desktop and tablet, which matters for staff moving between reception and consultation rooms. Usability feedback led to refinements such as clearer validation messages when required fields were missing and more logical flow from list views to detail and edit screens. Functionality testing of all CRUD paths and role restrictions confirmed the optimised version behaved reliably before this final evaluation.
The system appeals to its target audience because each role sees relevant tasks without unnecessary clutter. Administrators get full management capability; clinicians focus on patients and diagnoses; receptionists can register patients and check doctor details without exposure to settings they do not need. Against CareTrack’s requirements, the design and optimised MRMS are fit for purpose as a first digital record system, with known gaps (reporting, referrals, appointments) documented honestly rather than overstated.
BC.D3 – Individual responsibility, creativity and effective self-management in design, development and review
Throughout the project I took responsibility for my own work, as required by the brief. I completed research, designs, development and testing independently, kept authentication evidence accurate, and did not share assignment materials with other learners. I organised work across Activities 1–5 so that design informed development and testing informed optimisation, rather than leaving everything to the final development block.
Self-management was important because Activity 4 had the largest time allocation. I planned tasks in a logical order: database schema and models first, then API routes and CRUD, then role-based access, then front-end pages and dashboard, then test plans and user feedback. When tests failed or users reported confusion, I recorded the issue, fixed the specific problem and retested rather than making random changes. Keeping before and after screenshots and notes on what changed helped demonstrate responsibility during review and made this evaluation easier to support with real evidence.
Creativity appeared in how the solution was tailored to CareTrack rather than copied from a generic template. The branding and landing content explained MediCore’s relationship with CareTrack Clinic; the dashboard summarised counts and recent patients useful to administrators; patient profiles combined doctor and diagnosis information in one view. Design alternatives considered in Activity 2 (e.g. different dashboard layouts or navigation patterns) showed creative thinking about user needs before committing to one approach justified in Activity 3.
My skills and behaviours affected outcomes in practical ways. Stronger areas included implementing relational data and API endpoints, and applying feedback from peers or tutors to improve screens. Weaker areas included estimating time for polish and documentation—I sometimes left written justification until after coding, which meant catching up at the end of Activity 4. If repeating the unit, I would test each feature as soon as it was built and schedule a short mid-development review with a test user, not only at the end.
Personal performance also improved through the unit. I became more confident linking front-end forms to backend validation and role checks. Explaining design decisions to others in Activity 3 improved communication skills relevant to working with a real client. Taking ownership of errors found in testing (e.g. permission edge cases or form validation) and fixing them systematically showed professional behaviour expected of a junior developer at MediCore Solutions.
In summary, individual responsibility, creative problem-solving and structured self-management contributed directly to a working MRMS that CareTrack can review, use and extend. The evaluation in C.P6 and BC.D2 is grounded in that process—not only in what the final build looks like, but in how it was designed, tested, improved and reviewed with discipline across the whole assignment.
Conclusion
The MRMS successfully delivers the clinic’s priority needs: digital doctor, patient and diagnosis records, correct linking, search, role-based security and a usable interface for different staff roles. Design and optimisation choices support those goals and remain appropriate for a mid-sized private clinic. Honest limitations (extra services, advanced reporting, referrals) show where the project could grow next. Together, the evidence from all activities supports the conclusion that the solution is a credible first full stack release for CareTrack Clinic, produced through responsible and reflective practice across the full project lifecycle.
